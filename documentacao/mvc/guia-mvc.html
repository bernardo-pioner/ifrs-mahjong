O sistema não é um jogo de mahjong. É um programa para administrar um clube: pessoas, eventos, partidas e progresso. Várias telas ainda são placeholders — o grupo vai preenchê-las.

Conceito

1. O que é MVC

MVC é uma forma de organizar o código em três papéis. Cada um faz uma coisa só. Assim, um aluno pode mexer na tela sem quebrar o banco, e outro pode mexer nos dados sem redesenhar o HTML.

Model

Representa os dados e as regras de negócio. Fala com o SQLite. Não desenha HTML e não decide URL.

Controller

Recebe o pedido do navegador, chama o model se precisar e escolhe qual view mostrar. É o maestro.

View

É o HTML que a pessoa vê. Só apresenta dados que o controller enviou. Não grava no banco.

Navegadorpedido HTTP
→
Controllerdecide o que fazer
→
Modellê ou grava dados
→
Viewdevolve HTML

A analogia da cozinha: o controller é o garçom (anota o pedido), o model é a cozinha (prepara o prato), a view é o prato na mesa (o que o cliente vê).

Mapeamento

2. Como isso aparece neste projeto

Não usamos Laravel. É PHP vanilla, com pastas no lugar das camadas. O arquivo public/index.php só liga URL → método do controller. Ele não deve crescer com regra de negócio.

Passo a passo

4. Ciclo de um pedido HTTP

Depois do login, a tela inicial é o dashboard (URL /), não a de eventos. Eventos, partidas e o restante são telas seguintes, abertas pelos cards ou pelo menu.

  1. O aluno, já autenticado, abre http://localhost:8081/. O document root é public/.
  2. public/index.php carrega o bootstrap e registra: $router->get('/', [$dashboard, 'index']).
  3. O Router chama DashboardController::index().
  4. O controller exige login (requireAuth()). Se não houver sessão, redireciona para /login.
  5. O controller pede dados aos models: Member::count(), Event::count(), GameMatch::count(), ProgressNote::count().
  6. De volta ao controller, ele chama $this->view('dashboard', …). O HTML de views/dashboard.php entra no views/layout.php.
  7. O navegador mostra os cards. Só então, se a pessoa clicar em Eventos, começa um ciclo novo em /eventos.

5. O dashboard, peça por peça

O dashboard já está completo no padrão MVC. As outras funções (torneios, listagem de eventos, partidas, etc.) devem repetir este mesmo caminho:

→
Front controllerindex.php
→
ControllerDashboardController
→
Modelcount() no SQLite
→
Controllermonta $stats
→
Viewdashboard.php
→
Usuáriovê os cards

O model não fala com a view. O controller pede os dados, recebe os números e só então chama a view. Por isso o caminho volta ao controller no meio.

O que cada arquivo faz nesse pedido GET /

Ordem Papel Arquivo Responsabilidade
1 Usuário Navegador Já autenticado, pede http://localhost:8081/ (GET).
2 Front controller public/index.php Carrega o bootstrap, cria $dashboard = new DashboardController() e registra $router->get('/', [$dashboard, 'index']). O Router despacha para esse método.
3 Controller src/controllers/DashboardController.php index() chama requireAuth() (sem sessão, redireciona para /login) e pede totais aos models.
4 Model Member, Event, GameMatch, ProgressNote Cada um executa COUNT(*) na sua tabela via db(). Não conhecem HTML nem a URL.
5 Controller de novo mesmo DashboardController Junta os retornos em $stats e chama $this->view('dashboard', …). A view só recebe arrays prontos.
6 View views/dashboard.php + views/layout.php Imprime o nome e os quatro cards. O layout coloca a barra lateral. CSS em app.css.
7 Usuário Navegador Recebe o HTML. Clicar num card dispara um novo ciclo MVC (por exemplo GET /eventos).

Código real do controller

final class DashboardController extends Controller
{
    public function index(): void
    {
        $user = $this->requireAuth();          // sessão
        $this->view('dashboard', [
            'title' => 'Dashboard',
            'user' => $user,
            'currentPath' => '/',
            'stats' => [
                'members'  => Member::count(),       // model
                'events'   => Event::count(),        // model
                'matches'  => GameMatch::count(),    // model
                'progress' => ProgressNote::count(),
            ],
        ]);
    }
}

Código real de um model (Event)

final class Event
{
    public static function count(): int
    {
        return (int) db()->query('SELECT COUNT(*) FROM events')->fetchColumn();
    }
}

Os outros três models do dashboard (Member, GameMatch, ProgressNote) são iguais: só mudam a tabela. A view usa $stats['events'] etc. — nunca chama SQL.

Para implementar Torneios (hoje só um placeholder em PageController::torneios()), copie este desenho: rota em index.php → TorneioController → Torneio (model) → de volta ao controller → views/torneios/index.php → usuário. Não coloquem SQL na view e não desenhem HTML no model.

Para o grupo

7. Como adicionar uma tela nova

Repitam o dashboard. Imagine listar eventos de verdade, não só o placeholder. Siga esta ordem — não comece pelo HTML solto.

  1. Model. Em src/models/Event.php, crie métodos como all() ou create() com SQL via db() (PDO, prepared statements).
  2. Controller. Em EventController, um método index() busca os eventos no model e passa o array para a view. Um store() trata o POST do formulário.
  3. Rota. Em public/index.php: $router->get('/eventos', [$events, 'index']); e, se houver formulário, um post.
  4. View. Atualize views/events/index.php só com HTML e para imprimir dados já preparados. Use e() para escapar texto.
  5. CSS. Classes novas em public/assets/css/app.css (ou um CSS da página, como o login). Nada de style="…" no PHP.

Páginas ainda vazias (torneios, notícias, usuários, configurações) passam por PageController e views/coming-soon.php. Quando forem implementadas, criem controller + model próprios e troquem a rota.

Combinado

8. Regras básicas

  1. SQL fica no model. HTML fica na view. O controller só liga os dois.
  2. CSS em public/assets/css/. JavaScript em public/assets/js/. Sem style nem script no PHP das telas.
  3. Formulário POST leva csrfField(). Consulta no banco usa PDO com parâmetro (:nome), não concatena string.
  4. Senha grava com password_hash. Nunca em texto puro.
  5. Tabela nova ou coluna nova: alterar database/schema.sql e apagar data/app.sqlite para recriar o banco.

Laboratório

9. Como subir o sistema

Na raiz do projeto (a porta 8081 foi escolhida porque a 8080 já está em outro programa):

php -S localhost:8081 -t public

Abra http://localhost:8081. Entre com admin / admin. Depois de clonar o repositório, o SQLite é criado sozinho em data/app.sqlite na primeira execução.
